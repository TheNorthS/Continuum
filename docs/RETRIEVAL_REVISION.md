# 检索版本与缓存失效

知恒（Continuum）使用数据库维护的版本标记使检索缓存和本地索引快照失效。版本读取与文档数量解耦，不再查询并拼接全部就绪文档 ID；实时权限复核仍保留。

## 版本组成

| 数据 | 存放位置 | 作用 |
|---|---|---|
| 每库内容版本 | `knowledge_bases.retrieval_revision`，BIGINT，默认 0 | 标识该库可检索资料的变化 |
| 权限版本 | `security_state` 的 `retrieval_acl` 行 | 标识授权、角色、账号可用性和归属变化 |
| 数据库缓存命名空间 | `index_profiles` 的 `retrieval_cache` 行 | 为不同数据库隔离版本，避免相同库 ID / 计数撞键 |

`Repository.revision()` 每次实时计算“可读取知识库 ∩ 本轮所选知识库”，按库 ID 排序读取内容版本，再与数据库命名空间、权限版本一起计算 SHA-256。返回值为 `r3:` 加 64 位十六进制摘要，长度固定。

读取开销主要随可见知识库数量增长，不随文档数量增长。检索缓存键另外包含后端、Embedding 模型名、查询与候选数；新版本键与旧版本隔离，旧缓存由 TTL / LRU 淘汰。

## 事务内维护

Alembic `0006` 为 SQLite 和 PostgreSQL 安装数据库触发器，使用 `revision = revision + 1` 原子更新。版本和数据在同一事务提交或回滚，不依赖进程内计数器、Redis 自增或手工调用。

| 变化 | 版本行为 |
|---|---|
| 导入中的 `indexing` 文档及其片段 | 不提前使内容缓存失效 |
| 文档进入 `ready` | 对应库内容版本递增 |
| 文档离开 `ready` 或直接删除就绪文档 | 对应库内容版本递增 |
| 就绪文档的文件名、摘要、分块数或归属变更 | 对应库版本递增；跨库移动更新受影响的库 |
| 就绪文档的片段新增、删除、文本 / 元数据 / 向量原地修改 | 对应库内容版本递增，即使片段 ID 不变 |
| 事务失败或回滚 | 数据和版本一起回滚 |
| 角色权限、授权记录、账号角色 / 可用性、知识库归属变化 | 权限版本递增 |
| 普通登录、刷新、nonce 或审计状态更新 | 不因此修改检索版本 |

同值 SQL 更新不递增版本；重新加密会改变实际存储值，可触发保守失效。计数是失效代数，不是“文档操作次数”：多行更新可能增加多次，业务逻辑只比较是否相同。

内容更新按库失效：库 B 新增文档不会使只选择库 A 的内容版本变化。权限变更采用独立的全局版本，因此可能让其他库的缓存也失效；这一较少发生的操作换取了撤权后重授、角色权限恢复等情况下不复用旧权限代数的缓存。

## 并发读取

检索候选读取前后都会校验版本；期间资料或权限发生变化时，最多尝试三次，持续变化则返回 `retrieval_changed`（503），不把不匹配的结果当成稳定结果返回。本地索引重建也检查加载前后的版本，只有匹配后才发布快照。

版本校验不替代授权：缓存命中、精排后以及最终回答提交仍检查当前 ACL、知识库范围和资料就绪状态。它也不提供从请求开始到返回的全局写锁；检查结束后发生的新事务由下一次版本读取和后续权限复核处理。

图谱自身继续使用 Neo4j 图版本及 SQL 就绪资料范围；此变更不消除 Milvus 过滤或图谱遍历所需的文档范围查询。

## 升级与边界

先备份数据库和密钥，再按[升级指南](MIGRATION.md)应用 `0006`。开发环境仅在开启自动迁移时启动升级；生产先独立执行 `alembic upgrade head`，再重启所有 worker。本次迁移增加版本列、缓存命名空间和触发器，不重新生成模型向量。

SQLite / PostgreSQL 的普通 INSERT / UPDATE / DELETE（包括原始 SQL）经过触发器。禁用触发器、管理员直接修改版本字段、PostgreSQL `TRUNCATE`、外部仅修改 Milvus 的运维操作不属于自动失效保证；此类操作应停写维护、核对 SQL / 索引一致性，并更换缓存命名空间或清理相关缓存。数据库恢复或克隆时也应避免与旧环境共享缓存，命名空间会随备份一起复制。

专项回归包括迁移保真、回滚、并发递增、授权撤销与重授、跨库范围、本地快照和缓存读取期间版本变化。SQLite 测试为 `tests/test_retrieval_revision.py`；PostgreSQL 测试为 `tests/test_retrieval_revision_postgres.py`，需配置独立 `RAGE_TEST_POSTGRES_URL`，测试会创建并删除随机命名的测试数据库。

GitHub CI 的后端作业提供临时 PostgreSQL 16 服务并设置该测试地址，不需要生产凭据；触发方式仍为手动运行与 PR 自动检查。本地没有 PostgreSQL 时相关测试会明确跳过，不能据此声称已通过真实 PostgreSQL 验证。
